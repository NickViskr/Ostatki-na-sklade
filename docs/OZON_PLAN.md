## Реестр принятых решений (менять только по решению пользователя)
| Решение | Выбор |
|---|---|
| Дубли ручных и авто-заявок | Сопоставление по «отпечатку»: артикулы + количества + дата отгрузки (± окно) + назначение Ozon. С 26.07.2026 молчаливая автопривязка ОТКЛЮЧЕНА: заявка с совпавшим составом показывается в баннере новых поставок с меткой «Возможный дубль ручной отгрузки», привязка выполняется только вручную кнопкой «Привязать как дубль» на вкладке «Поставки Озон». Причина — критерий совпадения (точный состав + кабинет + даты ±5 дней) при типовых поставках мог привязать заявку к чужой похожей отгрузке, и остатки не списались бы |
| Доп. услуги | Только «сдаточные» (забор, упаковка, тариф по дате) считаются один раз при сдаче и входят в себестоимость. Хранение — отдельная метрика, в себестоимость поставки не входит. Распределение (с 20.07.2026): сервер (commitTransaction) начисляет долю доп. расходов пропорционально количеству на ВСЕ позиции Расхода — и комплекты, и обычные товары; клиент (ConfirmModal) для Расхода отправляет базовые parsedItems, чтобы не задваивать, итоговую себестоимость собирает сервер |
| Момент ухода остатка | Статус Ozon ACCEPTED_AT_SUPPLY_WAREHOUSE. Заявки до отгрузки (DATA_FILLING, READY_TO_SUPPLY) оформить нельзя; проверка — хелпер isStockDeparted («принято на точке отгрузки или дальше»), т.к. опрос 2 раза в сутки может проскочить статус. Отказ, отмена и просрочка отгрузкой не считаются |
| Услуги в автопилоте | Автопилот обнаруживает отгрузку → всплывающее окно с префиллом позиций и сдаточных услуг → без утверждения пользователем расход не создаётся |
| Опрос Ozon | 2 раза в сутки, 05:00 и 17:00 МСК: триггеры Apps Script (Europe/Moscow) → прокси Cloud Run (с 18.08.2026 — https://sklad-415081166309.europe-central2.run.app, именно он записан в `PROXY_URL` в Code.gs; старый адрес service-415081166309.us-west1.run.app оставлен как страховка и НЕ удалён, но автопилот через него больше не ходит) → Ozon Seller API → лист «Внешние отгрузки». Будильник — именно триггер Apps Script (Cloud Run засыпает). Плюс ручной запуск из Настроек |
| Недостача при приёмке | Остатки склада НЕ меняет. Стоимость разницы «отгружено − принято» перераспределяется на себестоимость товаров поставки. Каждая корректировка оставляет след в Истории |
| Пересорт | Признак: «заявлено X, принято меньше» + «заявлено 0, принято N». Проводится только после подтверждения пользователем. Ошибочный товар: списывается со склада + включается в состав поставки + услуги перераспределяются. Не уехавший: возвращается со своей базовой себестоимостью. Зеркалится во всех 6 путях учёта |
| Тестовая БД | Полная копия боевой; листы/колонки создаются идемпотентно (getOrCreateSheet); «Пользователи» чистится от паролей |
| Режим разработки | Тумблер только у админа, действует только в его браузере; запросы идут в тестовую БД; красная рамка + плашка «РЕЖИМ РАЗРАБОТКИ — ТЕСТОВАЯ БД» |
| Правило внедрения | Пункты 7–18 — только в режиме разработки на тестовой БД. Боевая база не участвует до п.20. Операции с остатками (пп. 12, 16) включаются только после просмотра «на показе» |
| Отмена поставки после проведённого списания | Остатки НЕ трогаются. Списание проводится только после фактической отгрузки, поэтому товар уже физически у Ozon и вернуться на свой склад не может (решение владельца 26.08.2026) |

Смена статусов внутри одной строки плана обязана давать ровно «1 1». Вставка нового пункта плана — ровно «2 0». Дозапись раздела в документацию — «N 0» с нулём удалений. Любое расхождение означает, что исполнитель разошёлся: правка ОТКАТЫВАЕТСЯ целиком, а не дочинивается поверх.

8. ОТКАТ ПО КОНТРОЛЬНОЙ СУММЕ. Повреждённый файл не чинится точечными правками. Выполняется `git checkout <SHA последнего целого коммита> -- <файл>`, резервный способ при недоступности git — `curl` на raw.githubusercontent.com по тому же SHA. Результат сверяется по `sha256sum` с эталоном, снятым архитектором ДО правки. При откате журналы НЕ ведутся: это технический откат, а не изменение проекта.

ОБЯЗАТЕЛЬНЫЕ ПРОВЕРКИ АРХИТЕКТОРА после каждой правки, до любого развёртывания:
- `git diff HEAD~1 --stat` — в коммите не должно быть файлов, которых не было в списке разрешённых;
- число пунктов плана до и после: `grep -cE '^- (⬜|🟨|✅) [0-9]+\.' docs/OZON_PLAN.md` — обязано совпадать, если промт не заводил новый пункт; на 01.08.2026 верный ответ 28;
- ВНИМАНИЕ, ГРАБЛИ. В первой редакции этого правила стояла команда с квадратными скобками: `grep -cE '^- [⬜🟨✅] [0-9]+\.'`. Она ВСЕГДА возвращает 0 и никогда не поймает потерю пункта, потому что символы ⬜🟨✅ многобайтовые, а квадратные скобки в grep -E разбираются побайтово. Правильная форма — чередование в круглых скобках, как выше; равнозначная альтернатива `LC_ALL=C.UTF-8 grep -cP '^- (⬜|🟨|✅) [0-9]+\.' docs/OZON_PLAN.md`. Любую проверочную команду, которую архитектор вписывает в промт, он обязан СНАЧАЛА выполнить у себя и убедиться, что она даёт осмысленный результат на текущем файле. Команда, выданная без проверки, создаёт ложное чувство защищённости и хуже, чем её отсутствие;
- ВНИМАНИЕ, ЛОЖНЫЙ ОТЧЁТ. 01.08.2026 исполнитель отчитался, что эта неработающая команда вернула 28, тогда как получить это значение она не могла в принципе. Цифра была вымышлена. Вывод: отчёт исполнителя подтверждает выполнение, но НЕ заменяет собственную проверку архитектора. Любое число из отчёта, на которое опирается решение, архитектор пересчитывает сам на свежесклонированном репозитории;
- контрольные суммы ключевых строк, которых правка не касалась: `sha256sum` по конкретным строкам через `sed -n 'Np'`;
- `git diff HEAD~1 --numstat -- docs/` — число удалённых строк в журналах обязано быть нулём;
- сверка размера файла в байтах с независимо рассчитанным ожидаемым значением: правки собираются архитектором локально и сравниваются с отчётом исполнителя побайтово.

Проверка «файл вырос, значит ничего не потеряно» НЕДОПУСТИМА и прямо запрещена: именно она пропустила инцидент 01.08.2026.
