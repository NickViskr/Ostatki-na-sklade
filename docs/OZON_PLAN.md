## Реестр принятых решений (менять только по решению пользователя)
| Решение | Выбор |
|---|---|
| Дубли ручных и авто-заявок | Сопоставление по «отпечатку»: артикулы + количества + дата отгрузки (± окно) + назначение Ozon. С 26.07.2026 молчаливая автопривязка ОТКЛЮЧЕНА: заявка с совпавшим составом показывается в баннере новых поставок с меткой «Возможный дубль ручной отгрузки», привязка выполняется только вручную кнопкой «Привязать как дубль» на вкладке «Поставки Озон». Причина — критерий совпадения (точный состав + кабинет + даты ±5 дней) при типовых поставках мог привязать заявку к чужой похожей отгрузке, и остатки не списались бы |
| Доп. услуги | Только «сдаточные» (забор, упаковка, тариф по дате) считаются один раз при сдаче и входят в себестоимость. Хранение — отдельная метрика, в себестоимость поставки не входит. Распределение (с 20.07.2026): сервер (commitTransaction) начисляет долю доп. расходов пропорционально количеству на ВСЕ позиции Расхода — и комплекты, и обычные товары; клиент (ConfirmModal) для Расхода отправляет базовые parsedItems, чтобы не задваивать, итоговую себестоимость собирает сервер |
| Момент ухода остатка | Статус Ozon ACCEPTED_AT_SUPPLY_WAREHOUSE. Заявки до отгрузки (DATA_FILLING, READY_TO_SUPPLY) оформить нельзя; проверка — хелпер isStockDeparted («принято на точке отгрузки или дальше»), т.к. опрос 2 раза в сутки может проскочить статус. Отказ, отмена и просрочка отгрузкой не считаются |
| Услуги в автопилоте | Автопилот обнаруживает отгрузку → всплывающее окно с префиллом позиций и сдаточных услуг → без утверждения пользователем расход не создаётся |
| Опрос Ozon | 2 раза в сутки, 05:00 и 17:00 МСК: триггеры Apps Script (Europe/Moscow) → прокси Cloud Run (https://service-415081166309.us-west1.run.app/) → Ozon Seller API → лист «Внешние отгрузки». Будильник — именно триггер Apps Script (Cloud Run засыпает). Плюс ручной запуск из Настроек |
| Недостача при приёмке | Остатки склада НЕ меняет. Стоимость разницы «отгружено − принято» перераспределяется на себестоимость товаров поставки. Каждая корректировка оставляет след в Истории |
| Пересорт | Признак: «заявлено X, принято меньше» + «заявлено 0, принято N». Проводится только после подтверждения пользователем. Ошибочный товар: списывается со склада + включается в состав поставки + услуги перераспределяются. Не уехавший: возвращается со своей базовой себестоимостью. Зеркалится во всех 6 путях учёта |
| Тестовая БД | Полная копия боевой; листы/колонки создаются идемпотентно (getOrCreateSheet); «Пользователи» чистится от паролей |
| Режим разработки | Тумблер только у админа, действует только в его браузере; запросы идут в тестовую БД; красная рамка + плашка «РЕЖИМ РАЗРАБОТКИ — ТЕСТОВАЯ БД» |
| Правило внедрения | Пункты 7–18 — только в режиме разработки на тестовой БД. Боевая база не участвует до п.20. Операции с остатками (пп. 12, 16) включаются только после просмотра «на показе» |

- ⬜ 25. Ускорение приложения: снять глобальный замок с операций чтения. Проблема замерена вживую 30.07.2026: при загрузке главной клиент делает 17 запросов к Apps Script, и они выстраиваются в очередь — 1,9 / 2,6 / 3,8 / 4,8 / 5,7 / 6,3 / 7,4 / 8,0 / 8,4 с, полная загрузка около 8,4 с. Причина НЕ в объёме данных: вся боевая БД это примерно 3 700 строк и 400 КБ, меньше 0,5% лимита Google Sheets в 10 млн ячеек; крупнейший лист «Продажи Ozon» (3 099 строк) имеет собственный потолок около 8–9 тыс. строк за счёт ретенции 78 недель и компакции старых недель в 28-дневные блоки. Причина в том, что doPost берёт LockService.getScriptLock() с waitLock(10000) на КАЖДЫЙ запрос, включая чтение, поэтому семнадцать параллельных запросов исполняются последовательно. Решение: замок берётся только для действий, изменяющих данные; читающие действия выполняются без него. Ожидаемый эффект — старт с 8,4 с до примерно 2 с. ОГРАНИЧЕНИЯ ЭТОГО ПУНКТА: список читающих действий составляется поимённо по фактическому коду, а не по префиксу «get» — любое действие, которое пишет хоть одну ячейку, включая автосоздание листов и идемпотентное самозаполнение дефолтами, остаётся под замком; отдельно выявить действия, которые читают и попутно пишут. Помнить про уже известный дедлок: runOzonSyncNow в doPost должен выполняться до waitLock. Проверка: замер времени загрузки главной до и после, затем регресс всех шести учётных путей на тестовой БД. Решение об отказе от разделения базы на две Google-таблицы (утверждено пользователем 30.07.2026): разделение прироста скорости не даёт, ломает целостность операций между листами, которые сейчас защищены одним замком, требует открывать второй файл через openById на каждый запрос и перебрать 53 вызова getDataRange() — признано нецелесообразным; вернуться к вопросу имеет смысл только для архивного файла «Истории» и только через несколько лет. РЕЗУЛЬТАТ АУДИТА ДЕРЕВА ВЫЗОВОВ (30.07.2026, рекурсивный обход по 44 пишущим API): полностью чистые чтения — getStock, getServiceRates, getUsers, getGlobalSettings, getServices (найденный в нём sort относится к JavaScript-массиву, а не к Range.sort); чтения с ленивой инициализацией — getTransactions и getSkus через ensureColumns дописывают колонку-заголовок, getExternalShipments, getOzonSupplyRequests и checkSupplyAvailability через getOrCreateSheet создают отсутствующий лист, getInitialData наследует и то и другое; худший случай этих операций безвреден, потому что два параллельных ensureColumns пишут одно значение в одну ячейку, а второй insertSheet просто вернёт ошибку одного запроса без порчи данных. Под замком остаётся getArchivedItems: он вызывает cleanOldArchivedItems, которая физически удаляет строки старше 60 дней через deleteRow в цикле. ВАЖНО ДЛЯ ВОЛНЫ 2: блок обхода switch на строке «if (action === 'getOzonStocks' || ...» удалять нельзя — у getFactoryOrders нет ветки в switch, а пять веток Ozon-чтений внутри switch содержат assertAdmin, которого блок обхода не выполняет, поэтому маршрутизация этих действий через switch отберёт доступ у неадминистраторов. Этапы: ✅ волна 1 (30.07.2026) — замок снят с шести действий загрузки главной: getInitialData, getStock, getTransactions, getSkus, getServices, getServiceRates; ⬜ волна 2 — после нескольких дней наблюдения за волной 1 добавить в список LOCK_FREE_ACTIONS ещё пять действий: getUsers, getGlobalSettings, getExternalShipments, getOzonSupplyRequests, checkSupplyAvailability; волна 2 разгружает обратные вызовы автоопроса Ozon и мастер поставки; ⬜ волна 3 (необязательная) — вынести cleanOldArchivedItems из getArchivedItems в отдельный суточный триггер, после чего getArchivedItems тоже можно освободить от замка.

## Известные хвосты вне плана
- Раздробление группы при восстановлении отгрузки комплекта из корзины: остатки корректны, страдает только группировка.
- При обновлении остатков Ozon возможна разовая ошибка кабинета code:2 — ретрая на уровне кабинета нет, лечится повторным нажатием, неполнота данных подсвечивается плашкой.
- Отмена заявки на поставку (/v1/supply-order/cancel) в приложении не реализована — ошибочная заявка убирается только вручную в Ozon Seller. Метод разведан, схема известна.
- Сверка «заявлено против принято» по артикулам через API недоступна: полей с фактически принятым количеством нет ни в /v3/supply-order/get, ни в /v1/supply-order/details, ни в /v1/supply-order/bundle. Разбор расхождений и согласование актов — только в личном кабинете.
- Устарело утверждение «клиентские правки деплоя не требуют»: server.ts раздаёт собранный фронтенд из dist, поэтому любое изменение в src/ в бою видно только после редеплоя Cloud Run.
- В ответе Ozon на черновик встречался кластер со статусом FULL_AVAILABLE, у которого при этом часть товара попадала в restricted_bundle_id (Уфа, 5 из 8 шт). Предположительно ограничение приёмки по конкретному SKU, статус кластера этого не отражает — наблюдать.
- Нет индикатора загрузки при обновлении таблицы склада (2–3 секунды тишины).
- Сырой технический текст ошибки Ozon показывается пользователю как есть.
- Массовое удаление в «Истории» неочевидно: кнопка появляется только после выбора галочек.
- Списание идёт по округлённой до копейки средней себестоимости — расхождение с точной средней до 0,04 ₽ на операцию, накопления не выявлено.
