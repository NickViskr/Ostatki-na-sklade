## Реестр принятых решений (менять только по решению пользователя)
| Решение | Выбор |
|---|---|
| Дубли ручных и авто-заявок | Сопоставление по «отпечатку»: артикулы + количества + дата отгрузки (± окно) + назначение Ozon. С 26.07.2026 молчаливая автопривязка ОТКЛЮЧЕНА: заявка с совпавшим составом показывается в баннере новых поставок с меткой «Возможный дубль ручной отгрузки», привязка выполняется только вручную кнопкой «Привязать как дубль» на вкладке «Поставки Озон». Причина — критерий совпадения (точный состав + кабинет + даты ±5 дней) при типовых поставках мог привязать заявку к чужой похожей отгрузке, и остатки не списались бы |
| Доп. услуги | Только «сдаточные» (забор, упаковка, тариф по дате) считаются один раз при сдаче и входят в себестоимость. Хранение — отдельная метрика, в себестоимость поставки не входит. Распределение (с 20.07.2026): сервер (commitTransaction) начисляет долю доп. расходов пропорционально количеству на ВСЕ позиции Расхода — и комплекты, и обычные товары; клиент (ConfirmModal) для Расхода отправляет базовые parsedItems, чтобы не задваивать, итоговую себестоимость собирает сервер |
| Момент ухода остатка | Статус Ozon ACCEPTED_AT_SUPPLY_WAREHOUSE. Заявки до отгрузки (DATA_FILLING, READY_TO_SUPPLY) оформить нельзя; проверка — хелпер isStockDeparted («принято на точке отгрузки или дальше»), т.к. опрос 2 раза в сутки может проскочить статус. Отказ, отмена и просрочка отгрузкой не считаются |
| Услуги в автопилоте | Автопилот обнаруживает отгрузку → всплывающее окно с префиллом позиций и сдаточных услуг → без утверждения пользователем расход не создаётся |
| Опрос Ozon | 2 раза в сутки, 05:00 и 17:00 МСК: триггеры Apps Script (Europe/Moscow) → прокси Cloud Run (https://service-415081166309.us-west1.run.app/) → Ozon Seller API → лист «Внешние отгрузки». Будильник — именно триггер Apps Script (Cloud Run засыпает). Плюс ручной запуск из Настроек |
| Недостача при приёмке | Остатки склада НЕ меняет. Стоимость разницы «отгружено − принято» перераспределяется на себестоимость товаров поставки. Каждая корректировка оставляет след в Истории |
| Пересорт | Признак: «заявлено X, принято меньше» + «заявлено 0, принято N». Проводится только после подтверждения пользователем. Ошибочный товар: списывается со склада + включается в состав поставки + услуги перераспределяются. Не уехавший: возвращается со своей базовой себестоимостью. Зеркалится во всех 6 путях учёта |
| Тестовая БД | Полная копия боевой; листы/колонки создаются идемпотентно (getOrCreateSheet); «Пользователи» чистится от паролей |
| Режим разработки | Тумблер только у админа, действует только в его браузере; запросы идут в тестовую БД; красная рамка + плашка «РЕЖИМ РАЗРАБОТКИ — ТЕСТОВАЯ БД» |
| Правило внедрения | Пункты 7–18 — только в режиме разработки на тестовой БД. Боевая база не участвует до п.20. Операции с остатками (пп. 12, 16) включаются только после просмотра «на показе» |

## Правило ведения журналов

Записи в `docs/DEVLOG.md`, `docs/CHANGELOG.md` и `docs/TEST_LOG.md` добавляются ТОЛЬКО в самый конец файла. Правило введено 01.08.2026 после того, как выяснилось, что в верхней части журналов лежит исторический блок с обратным порядком дат, а новые записи дописываются вниз, и из-за этой двойственности исполнитель несколько раз редактировал чужие строки.

1. `DEVLOG.md` и `TEST_LOG.md` — новая запись это новая последняя строка таблицы.
2. `CHANGELOG.md` — новая запись это новый блок `## [ГГГГ-ММ-ДД]` в конце файла, даже если блок с такой же датой уже есть выше. Сливать блоки с одинаковой датой запрещено.
3. Ни одна существующая строка не редактируется, не переносится, не удаляется и не переформатируется. Опечатки в старых записях не исправляются.
4. Верхняя часть файлов и исторический блок с обратным порядком дат не трогаются никогда.
5. Проверка архитектором обязательна до развёртывания: `git diff HEAD~1 --numstat -- docs/DEVLOG.md docs/CHANGELOG.md docs/TEST_LOG.md`. Второй столбец, число удалённых строк, обязан быть нулём для всех трёх файлов. Любое ненулевое значение считается нарушением и разбирается до деплоя.
